# 스키마 검색 비교 평가 보고서

- 평가 목적: SQL 생성에 필요한 테이블의 검색 성능 비교
- 평가 대상: BEAVER `dw` 도메인의 테이블 97개, 질의 500건, 검색 방식 5종
- 주요 비교 기준: Macro Recall 내림차순
- 보조 지표: Micro Recall, Precision, F1, 완전 일치율, 응답시간
- 최고 Macro Recall: LLM 기반 스키마 검색 (gpt-6-luna), 59.53%

## 1. 데이터셋과 전처리

### 1.1. 사용 데이터셋과 실제 평가 범위

- 질의·정답 데이터: Hugging Face `beaverbench/beaver-query`의 `dw` split
- 테이블 메타데이터: Hugging Face `beaverbench/beaver-table`의 `dw` split
- BEAVER 특성: 기업 환경의 복잡한 Text-to-SQL 문제를 위한 벤치마크
- 본 평가 범위: SQL 생성 이전의 테이블 검색 단계

| 구분 | 규모 | 내용 및 역할 |
|---|---:|---|
| `beaver-table`, `dw` | 97개 테이블 | 테이블명, 컬럼명·자료형, 행·컬럼 예시 |
| `beaver-query`, `dw` 원본 | 5,787개 질의 | 자연어 질문, SQL, 정답 테이블, 조인 키, 도메인 지식 등 |
| 실제 평가 집합 | 500개 질의 | 원본 앞 500건인 `dw_0`~`dw_499` |
| 검색 카탈로그 | 97개 테이블 | `table_name`, `schema`(DDL), `description` |

- 평가 부분집합: 원본 앞 500건과 전체 레코드 내용 동일; 무작위 추출 표본에 해당하지 않음
- 질의 범주: 500건 모두 `domain-specific complex query`; 도메인 지식과 복잡한 SQL 구조를 함께 다루는 질의
- 정답 테이블 수: 2개인 문항 195건, 3개인 문항 305건
- 정답 테이블 출현 횟수: 문항별 합계 1,305개, 문항당 평균 2.61개
- 결과 적용 범위: `dw` 전체 5,787건이 아닌 해당 500건의 평가 결과

### 1.2. 테이블 정보 전처리

1. `dw` 도메인에 속한 테이블 메타데이터 97개 수집
2. `column_names`, `column_types`, `example_rows`, `example_columns`의 JSON 문자열을 리스트·객체 등 구조화된 값으로 복원
3. 나머지 필드와 이미 구조화된 값 보존; 전체 레코드를 UTF-8 JSON 배열로 저장
4. 컬럼명과 자료형 개수의 일치 여부 검증; 동일 테이블명은 첫 레코드만 유지
5. 테이블명·컬럼명·자료형을 조합해 `CREATE TABLE` DDL 구성; 별도의 PK·FK 제약조건 생성 없음
6. 테이블명과 DDL을 Local LLM(DeepSeek)에 입력해 주요 조회 목적·컬럼 역할 중심의 한국어 테이블 설명(table description) 생성
7. 테이블명·DDL·설명으로 검색 카탈로그 구성; 전처리 산출물과 실제 검색 카탈로그의 내용 일치 확인

- 테이블 설명: Local LLM(DeepSeek)으로 생성한 전처리 정보; BEAVER 원본 주석과 구분
- Local LLM(DeepSeek) 활용 범위: 테이블 설명의 사전 생성에 사용; DeepSeek 기반 온라인 검색의 평가 여부와 별개

### 1.3. 질의 정보 전처리

1. `dw` 도메인의 질의 5,787건 수집
2. `tables`, `join_keys`, `column_mapping`, `domain_knowledge`, `sub_questions`, `sub_sqls`의 JSON 문자열을 리스트·객체 등 구조화된 값으로 복원
3. `id`, `category`, `detailed_category`, `contains_domain_knowledge`, `db`, `question`, `sql` 등 나머지 필드 보존; UTF-8 JSON 배열로 저장
4. 원본 앞 500건으로 평가 입력 구성; `id`는 문항 식별, `question`은 검색 질의, `tables`는 정답 테이블로 사용

- 정답 기준: SQL에서 다시 추출한 테이블이 아닌 데이터셋의 `tables` 주석
- 검색 입력 제외 정보: 정답 SQL, 조인 키, 컬럼 매핑, 도메인 지식 주석, 하위 질문·SQL
- 평가 히스토리: 모든 문항에서 빈 배열 사용

## 2. 검색 방식별 동작

### 2.1. 공통 입력과 모델

- 공통 입력: 현재 질의 `query`, 과거 대화 `history`
- 히스토리 형식: 오래된 순서의 `user`·`assistant` 메시지 목록
- 실제 사용 범위: 최근 메시지 최대 3개인 `history[-3:]`과 현재 질의
- turn 기준: 메시지 하나를 1 turn으로 취급; 현재 질의는 최근 메시지 3개 제한에서 제외
- 임베딩 입력 구성: 최근 메시지의 `role: content`와 현재 질의의 `user: query`를 순서대로 결합; 히스토리가 없으면 질의 문자열만 사용
- LLM 입력 구성: 최근 히스토리를 대화 메시지로 전달; 마지막 사용자 메시지에 현재 질의와 테이블·후보 정보 포함

| 용도 | 모델 | 벡터 차원 |
|---|---|---:|
| 테이블 임베딩 | `BAAI/bge-m3` | 1,024 |
| 테이블·triplet 임베딩 | `text-embedding-3-small` | 1,536 |
| 테이블 선택·관계 생성 | `gpt-6-luna` | 해당 없음 |

- 모델 확인 기준: 현재 설정·인덱스 메타데이터·별도 응답 기록; 평가 JSON 자체에는 모델명 별도 저장 없음
- 공통 반환 정보: 테이블명, DDL, 설명; 각 목록의 같은 위치가 같은 테이블에 대응
- 품질 평가 대상: 반환 정보 중 테이블명만 사용

### 2.2. 임베딩 기반 스키마 검색 (bge-m3)

- 사전 준비: 테이블명·설명을 `BAAI/bge-m3`로 임베딩; DDL은 반환용 정보로 보관
- 벡터 저장: L2 정규화 후 FAISS `IndexFlatIP`에 저장; 정규화 벡터의 내적으로 코사인 유사도 계산
- 인덱스 규모: 테이블 97개, 1,024차원

1. 저장된 테이블 인덱스와 대응 레코드 로드
2. 질의·최근 히스토리를 같은 모델로 임베딩하고 L2 정규화
3. 코사인 유사도 상위 `top_k`개 테이블 선택; 인덱스가 작으면 저장된 개수까지 반환
4. 선택된 테이블명과 저장된 DDL·설명 반환

### 2.3. 임베딩 기반 스키마 검색(text-embedding-3-small)

- 사전 준비: 테이블명·설명을 `text-embedding-3-small`로 임베딩; DDL은 임베딩 입력에서 제외하고 반환용 정보로 보관
- 인덱스 구성: OpenAI 전용 인덱스에 테이블 97개의 1,536차원 벡터 저장
- 검색 절차: 질의·최근 히스토리 임베딩 → L2 정규화 → 코사인 유사도 상위 `top_k`개 테이블 선택 → DDL·설명 반환
- 테이블 임베딩 시점: 사전 인덱싱 단계; 요청별 전체 테이블 재임베딩 없음

### 2.4. 임베딩 기반 triplet 검색 (gpt-6-luna, text-embedding-3-small)

- 사전 준비: 관계 triplet 생성과 임베딩 인덱싱 수행

1. 전체 테이블명·DDL·설명을 `gpt-6-luna`에 입력해 테이블 간 관계 생성
2. `[주체 테이블 정보, 영문 관계 표현, 객체 테이블 정보]` 형태로 triplet 구성; 테이블 정보에 원본 테이블명·설명 포함
3. 카탈로그 외 테이블 참조 검증; 동일 주체·관계·객체 조합 중복 제거
4. 주체 테이블명·설명, 관계 표현, 객체 테이블명·설명을 결합해 `text-embedding-3-small`로 임베딩; DDL은 임베딩 입력에서 제외
5. L2 정규화 후 FAISS 인덱스에 저장; 현재 저장 규모는 triplet 159개, 1,536차원

- 온라인 검색 절차

1. 질의·최근 히스토리를 같은 임베딩 모델로 변환하고 정규화
2. 저장된 모든 triplet과의 코사인 유사도 계산
3. 각 triplet의 유사도를 주체·객체 테이블에 부여; 테이블별 최대 유사도를 대표 점수로 집계
4. 점수순으로 서로 다른 테이블 `top_k`개 선택; 동점은 테이블명 순으로 정렬
5. 원본 카탈로그에서 선택된 테이블의 DDL·설명을 매핑해 반환

- 검색 후보 범위: triplet에 등장하고 원본 카탈로그에 매핑되는 테이블; 현재 저장된 triplet의 참여 테이블은 90개
- 온라인 LLM 재선별: 수행하지 않음; 관계 생성에만 사전 사용
- 관계의 의미: 스키마·설명에서 추론한 의미 관계; 검증된 외래 키·조인 조건 보장 없음
- 저장 이력 한계: 평가 JSON에 사용한 triplet의 버전·해시 기록 없음; 위 규모는 현재 저장 자료 기준

### 2.5. LLM 기반 스키마 검색 (gpt-6-luna)

1. 전체 테이블 97개의 카탈로그 로드
2. 질의·최근 히스토리·전체 테이블명·DDL·설명을 `gpt-6-luna`에 입력
3. 조회·필터·집계·테이블 연결에 필요한 테이블명과 선정 근거를 구조화된 형태로 선택
4. 선택된 이름의 카탈로그 포함 여부 검증 및 중복 제거
5. 선택된 테이블의 원본 DDL·설명 반환

- 일반적인 요청의 LLM 호출 수: 1회
- 반환 개수: 고정 `top_k` 제한 없음; 관련 테이블이 없으면 빈 목록 허용
- 사전 검색 자료: 별도 임베딩 인덱스·triplet 사용 없음

### 2.6. LLM 기반 triplet 검색(gpt-6-luna)

- 사전 준비: 전체 테이블명·DDL·설명을 바탕으로 `gpt-6-luna`가 관계 triplet 생성

1. 질의·최근 히스토리·전체 테이블명·설명을 `gpt-6-luna`에 입력해 시작 후보 선택
2. 시작 후보에서 저장된 관계를 양방향으로 최대 2단계 확장
3. 시작 후보를 포함한 확장 후보의 테이블명·DDL·설명과 후보 간 관계 구성
4. 질의·최근 히스토리·후보 정보를 `gpt-6-luna`에 입력해 최종 테이블 재선별
5. 후보 집합 내부의 선택 여부 검증 및 원본 DDL·설명 반환

- 일반적인 요청의 LLM 호출 수: 시작 후보 선택 1회, 최종 재선별 1회
- 첫 번째 호출 입력: 전체 테이블명·설명; DDL 제외
- 두 번째 호출 입력: 확장 후보의 DDL·설명과 원래 방향을 유지한 관계 표현
- 예외 처리: 시작 후보가 없으면 그래프 확장·두 번째 LLM 호출 생략
- 독립 테이블 처리: 관계가 없는 테이블도 시작 후보로 선택 가능
- 반환 개수: 고정 `top_k` 제한 없음

### 2.7. Local LLM(DeepSeek) 검색 평가 현황

- 진행 현황: 운영서버 이관 작업 진행 중
- 평가 상태: 검색 성능 평가 미수행; 품질·지연시간 비교에서 제외
- 평가 범위 구분: 테이블 설명의 사전 생성 및 bge-m3 임베딩 검색 평가와 별개

## 3. 평가 지표와 결과 JSON 해석

- 평가 방식: 문항별 순차 요청
- 공통 요청 조건: `query=question`, `history=[]`, 타임아웃 300초
- 임베딩 검색 3종: `top_k=5`
- LLM 검색 2종: `top_k` 전달 없음; 반환 개수 가변

### 3.1. 결과 구조

| 필드 | 의미 |
|---|---|
| `format_version` | 평가 JSON 형식 버전; 현재 모두 `1` |
| `configuration.endpoint`, `base_url` | 평가한 검색 기능과 서버 주소 |
| `configuration.top_k` | 임베딩 검색의 반환 개수 설정; LLM 검색은 `null` |
| `configuration.timeout_seconds` | 문항별 요청 타임아웃 |
| `configuration.dataset_path`, `dataset_sha256` | 입력 위치와 파일 바이트 전체의 SHA-256; 공백·직렬화 형식 변경에도 해시 변경 가능 |
| `state` | 실행 상태인 `running`, `interrupted`, `complete`; 검색 정답률과 별개 |
| `started_at`, `updated_at` | 실행 시작·마지막 저장 시각; UTC 오프셋 포함 |
| `summary` | 전체 처리 현황과 성공 응답의 집계 지표 |
| `results` | 문항별 질문·정답·예측 테이블·지표·처리시간·오류 |

- 실행 시각 해석: 재개·중단·저장 비용 포함 가능; 시작·갱신 시각 차이를 순수 검색시간으로 사용하지 않음

### 3.2. 문항별 검색 품질

- 표기: 정답 테이블 집합 `G`, 검색된 테이블 집합 `P`

| 지표 | 계산 | 의미 |
|---|---|---|
| `tp` | `len(G ∩ P)` | 올바르게 찾은 정답 테이블 수 |
| `fp` | `len(P - G)` | 정답에 없는 추가 테이블 수 |
| `fn` | `len(G - P)` | 찾지 못한 정답 테이블 수 |
| `recall` | `TP / (TP + FN)` | 필요한 테이블 중 검색으로 확보한 비율; 본 비교의 주요 지표 |
| `precision` | `TP / (TP + FP)` | 반환한 테이블 중 정답의 비율 |
| `f1` | `2 × TP / (2 × TP + FP + FN)` | Precision·Recall을 함께 반영한 지표 |
| `exact_match` | `G == P` | 누락·불필요한 추가가 없는 완전 일치 여부 |

- 분모가 0인 비율: `0.0` 적용
- 집합 비교 방식: 중복 테이블·반환 순서의 점수 영향 없음; 테이블명 대소문자 자동 보정 없음
- 평가 제외 지표: MRR·nDCG, 컬럼 검색 정확도, SQL 실행 정확도
- 계산 예시: 정답 `{A, B}`, 예측 `{A, C, D}` → TP=1, FP=2, FN=1
- 예시 점수: Recall 50.00%, Precision 33.33%, F1 40.00%, 완전 일치 `false`
- 완전 일치 조건: Recall 100% 확보와 불필요한 추가 테이블 부재를 모두 충족

### 3.3. 집계 지표와 처리 현황

| `summary` 필드 | 의미 |
|---|---|
| `total_count` | 입력 전체 문항 수 |
| `evaluated_count` | 성공·실패를 포함한 저장 결과 문항 수 |
| `success_count`, `failure_count` | 정상 응답 검증 성공 수·오류 수 |
| `pending_count` | `total_count - evaluated_count`; 아직 결과가 없는 문항 수 |
| `success_rate` | `success_count / evaluated_count`; 검색 정답률이 아닌 응답 처리 성공률 |
| `macro.precision`, `macro.recall`, `macro.f1` | 성공 문항별 각 지표의 단순 평균 |
| `micro.tp`, `micro.fp`, `micro.fn` | 성공 문항 전체의 TP·FP·FN 합계 |
| `micro.precision`, `micro.recall`, `micro.f1` | 전체 TP·FP·FN 합계로 계산한 지표 |
| `exact_match_rate` | 성공 문항 중 완전 일치한 비율 |
| `mean_latency_seconds` | 성공 문항의 클라이언트 측 요청·응답 처리시간 평균(초) |
| `mean_api_elapsed_time` | 성공 문항 중 유효한 서버 `elapsed_time`의 평균(초) |

- Macro 집계: 문항별 동일 비중; **Macro F1은 문항별 F1의 평균**
- Micro 집계: 테이블 출현 횟수 합산; 정답·예측 테이블이 많은 문항의 영향 증가
- 클라이언트 시간 범위: HTTP 요청 전부터 응답 검증·지표 계산 후까지; 네트워크 왕복·클라이언트 처리 포함
- 서버 시간 범위: 서버가 보고한 API 내부 처리시간
- 시간 집계 제외: 사전 테이블 임베딩·triplet 생성·triplet 인덱싱
- 실패 문항 처리: 품질·평균 지연 지표에서 제외; 실패를 0점이나 타임아웃 시간으로 포함하지 않음
- 미집계 값: 성공 문항이 없으면 품질·평균 지연 지표 `null`; 유효한 서버 시간이 없으면 서버 평균 `null`
- 결과 확인 원칙: 품질 지표와 성공률·실패 수를 함께 확인

### 3.4. 개별 결과와 실패 원인 확인

- 문항 식별: `index`, `id`, `question`
- 정답·검색 결과 비교: `expected_tables`, `predicted_tables`
- 문항별 품질: `metrics`의 TP·FP·FN, Recall·Precision·F1, 완전 일치 여부
- 처리시간·시각: `latency_seconds`, `api_elapsed_time`, `completed_at`
- `status=success`: HTTP 성공, API 성공 상태, 반환 목록의 형식·길이 검증 통과
- 성공 상태의 의미: 정답 테이블 선택 여부와 별개; 빈 목록도 정상 형식이면 성공 처리 가능
- `status=error`: `http_status`, `error.type`, `error.message`로 원인 확인; 예측 테이블·지표는 `null`
- 주요 오류 유형: `http_error`(HTTP 오류), `api_error`(API 오류 상태), `invalid_response`(응답 형식 오류), 연결·타임아웃 예외
- 재개 처리: 성공 결과 재사용, 실패·미평가 문항 재호출
- 재개 검증: 검색 기능·서버 주소·`top_k`·데이터셋 해시 등의 일치 여부 확인
