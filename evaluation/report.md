# 테이블 스키마 검색 방법 평가

- 평가 목적: SQL 생성에 필요한 테이블의 검색 성능 비교
- 평가 대상: BEAVER `dw` 도메인의 테이블 97개, 질의 500건, 검색 기능 10종·설정 조합 18개
- 주요 비교 기준: 성공 문항 기준 Macro Recall 내림차순
- 보조 지표: Micro Recall, Precision, F1, 완전 일치율, 처리 성공률, 응답시간, 반환 테이블 수
- 최고 Macro Recall: 임베딩 시작점 기반 triplet 확장 검색 (text-embedding-3-small), 시작점 2개·2-hop 조건의 86.10%
- 비교 조건 구분: 고정 top-5 검색과 관계 확장 후보 전체 반환 방식의 차이 반영

## 1. 데이터셋과 전처리

### 1.1. 사용 데이터셋과 실제 평가 범위

- 질의·정답 데이터: Hugging Face `beaverbench/beaver-query`의 `dw` split
- 테이블 메타데이터: Hugging Face `beaverbench/beaver-table`의 `dw` split
- BEAVER 특성: 기업 환경의 복잡한 Text-to-SQL 문제를 위한 벤치마크
- 본 평가 범위: SQL 생성 이전의 테이블 검색 단계

| 구분 | 규모 | 내용 및 역할 |
|---|---:|---|
| `beaver-table`, `dw` | 97개 테이블 | 테이블명, 컬럼명·자료형, 행·컬럼 예시 |
| `beaver-query`, `dw` 원본 | 5,787개 질의 | 자연어 질문, SQL, 정답 테이블, 조인 키, 도메인 지식 등 |
| 실제 평가 집합 | 500개 질의 | 원본 앞 500건인 `dw_0`~`dw_499` |
| 검색 카탈로그 | 97개 테이블 | `table_name`, `schema`(DDL), `description` |

- 평가 부분집합: 원본 앞 500건과 전체 레코드 내용 동일; 무작위 추출 표본에 해당하지 않음
- 질의 범주: 500건 모두 `domain-specific complex query`; 도메인 지식과 복잡한 SQL 구조를 함께 다루는 질의
- 정답 테이블 수: 2개인 문항 195건, 3개인 문항 305건
- 정답 테이블 출현 횟수: 문항별 합계 1,305개, 문항당 평균 2.61개
- 결과 적용 범위: `dw` 전체 5,787건이 아닌 해당 500건의 평가 결과

### 1.2. 테이블 정보 전처리

1. `dw` 도메인에 속한 테이블 메타데이터 97개 수집
2. `column_names`, `column_types`, `example_rows`, `example_columns`의 JSON 문자열을 리스트·객체 등 구조화된 값으로 복원
3. 나머지 필드와 이미 구조화된 값 보존; 전체 레코드를 UTF-8 JSON 배열로 저장
4. 컬럼명과 자료형 개수의 일치 여부 검증; 동일 테이블명은 첫 레코드만 유지
5. 테이블명·컬럼명·자료형을 조합해 `CREATE TABLE` DDL 구성; 별도의 PK·FK 제약조건 생성 없음
6. 테이블명과 DDL을 Local LLM(DeepSeek)에 입력해 주요 조회 목적·컬럼 역할 중심의 한국어 테이블 설명(table description) 생성
7. 테이블명·DDL·설명으로 검색 카탈로그 구성; 전처리 산출물과 실제 검색 카탈로그의 내용 일치 확인

- 테이블 설명: Local LLM(DeepSeek)으로 생성한 전처리 정보; BEAVER 원본 주석과 구분
- 전처리·검색 실행 구분: 테이블 설명은 Local LLM(DeepSeek)으로 사전 생성; 본 보고서의 DeepSeek 검색·관계 생성은 OpenRouter 경로 기준

### 1.3. 질의 정보 전처리

1. `dw` 도메인의 질의 5,787건 수집
2. `tables`, `join_keys`, `column_mapping`, `domain_knowledge`, `sub_questions`, `sub_sqls`의 JSON 문자열을 리스트·객체 등 구조화된 값으로 복원
3. `id`, `category`, `detailed_category`, `contains_domain_knowledge`, `db`, `question`, `sql` 등 나머지 필드 보존; UTF-8 JSON 배열로 저장
4. 원본 앞 500건으로 평가 입력 구성; `id`는 문항 식별, `question`은 검색 질의, `tables`는 정답 테이블로 사용

- 정답 기준: SQL에서 다시 추출한 테이블이 아닌 데이터셋의 `tables` 주석
- 검색 입력 제외 정보: 정답 SQL, 조인 키, 컬럼 매핑, 도메인 지식 주석, 하위 질문·SQL
- 평가 히스토리: 모든 문항에서 빈 배열 사용

## 2. 검색 방식별 동작

### 2.1. 공통 입력과 모델

- 공통 입력: 현재 질의 `query`, 오래된 순서의 `user`·`assistant` 메시지 목록 `history`
- 실제 사용 범위: 최근 메시지 최대 3개인 `history[-3:]`과 현재 질의; 메시지 하나를 1 turn으로 취급
- 임베딩 입력: 최근 메시지의 `role: content`와 현재 질의를 결합; 히스토리가 없으면 질의 원문만 사용
- LLM 입력: 최근 히스토리를 대화 메시지로 전달; 마지막 사용자 메시지에 현재 질의와 기능별 카탈로그·후보 정보 포함
- 공통 반환 정보: 테이블명·원본 DDL·설명; 품질 평가는 테이블명 집합 기준
- 평가 대상 선정: 엔드포인트 전체 목록에서 평가된 검색 계열과 현재 저장 결과를 대조; hybrid의 시작점 2개 조합도 포함

| 용도 | 모델·실행 경로 | 현재 저장 자료 |
|---|---|---|
| 테이블 임베딩 | `BAAI/bge-m3` | 97개 테이블, 1,024차원 |
| 테이블 임베딩 | `text-embedding-3-small` | 97개 테이블, 1,536차원 |
| Triplet 임베딩 | `BAAI/bge-m3` | 243개 triplet, 1,024차원 |
| Triplet 임베딩 | `text-embedding-3-small` | 159개 triplet, 1,536차원 |
| OpenAI 테이블 선택·관계 생성 | `gpt-6-luna` | 관계 159개, 참여 테이블 90개 |
| OpenRouter 테이블 선택·관계 생성 | `deepseek/deepseek-v4-flash-0731` | 관계 243개, 참여 테이블 97개 |

- DeepSeek 온라인 검색: OpenRouter를 통한 전체 스키마 검색·LLM 시작점 기반 확장 검색의 평가 결과 사용
- 모델·관계 규모의 근거: 현재 설정·인덱스·생성 응답 기록; 평가 JSON 자체에는 모델명·RDF 버전·해시의 완전한 이력 없음
- 관계 의미: LLM이 스키마·설명에서 추론한 의미 관계; 검증된 외래 키·조인 조건 보장 없음

### 2.2. 임베딩 기반 스키마 검색

- 검색 기능: 임베딩 기반 스키마 검색 (bge-m3), 임베딩 기반 스키마 검색(text-embedding-3-small)

1. 테이블명·설명을 각 임베딩 모델로 사전 변환; DDL은 반환용 정보로 보관
2. 벡터를 L2 정규화한 뒤 모델별 FAISS `IndexFlatIP`에 저장
3. 질의·최근 히스토리를 같은 모델로 임베딩하고 정규화
4. 정규화 벡터의 내적으로 코사인 유사도 계산; 상위 5개 테이블 선택
5. 인덱스에 저장된 테이블명·DDL·설명 반환

- 평가 설정: 두 모델 모두 최종 스키마 5개 반환; 관계 확장·온라인 LLM 호출 없음
- 테이블 임베딩 시점: 사전 준비 단계; 질의마다 전체 테이블 재임베딩 없음

### 2.3. 임베딩 기반 triplet 검색

- 검색 기능: 임베딩 기반 triplet 검색 (DeepSeek/OpenRouter, bge-m3), 임베딩 기반 triplet 검색 (gpt-6-luna, text-embedding-3-small)

1. 전체 테이블명·DDL·설명을 공급자별 LLM에 입력해 관계 triplet 생성
2. `[주체 테이블 정보, 영문 관계 표현, 객체 테이블 정보]`로 구성; 원본 테이블명·설명 부착 및 동일 관계 중복 제거
3. 주체 이름·설명, 관계 표현, 객체 이름·설명을 결합해 임베딩; DDL 자체는 임베딩 입력에서 제외
4. 질의·최근 히스토리를 같은 모델로 임베딩하고 모든 triplet과의 코사인 유사도 계산
5. 주체·객체에 유사도 부여; 테이블별 참여 triplet의 최대 유사도로 점수 집계
6. 고유 테이블 상위 5개 선택; 동점은 테이블명 순으로 정렬하고 현재 카탈로그의 DDL·설명 반환

- 평가 설정: 두 모델 모두 최종 스키마 5개 반환; triplet 5개를 그대로 반환하는 방식과 구분
- 온라인 LLM 호출·관계 확장: 없음; LLM은 관계 사전 생성에 사용
- 후보 범위: 인덱스에 등장하고 현재 카탈로그에 매핑되는 테이블
- bge-m3 계열 준비: 일반 RDF가 없으면 OpenRouter 생성 RDF를 이용하는 대체 경로 지원; 현재 저장 관계는 OpenRouter 기준
- 비교 시 유의점: 임베딩 모델뿐 아니라 생성 관계·테이블 포함 범위도 다름

### 2.4. LLM 기반 스키마 검색

- 검색 기능: LLM 기반 스키마 검색 (gpt-6-luna), LLM 기반 스키마 검색 (DeepSeek/OpenRouter)

1. 전체 테이블 97개의 이름·DDL·설명 로드
2. 질의·최근 히스토리·전체 카탈로그를 공급자별 LLM에 입력
3. 조회·필터·집계·연결에 필요한 테이블명과 선정 근거 선택
4. 카탈로그 포함 여부 검증·중복 제거 후 선택된 테이블의 원본 스키마 반환

- 온라인 LLM 호출: 일반적인 요청에서 1회
- 반환 개수: 고정 제한 없음; `top_k`·`max_hop` 사용 없음
- 사전 준비 자료: 임베딩 인덱스·RDF 불필요

### 2.5. LLM 시작점 기반 triplet 확장 검색

- 검색 기능: LLM 시작점 기반 triplet 확장 검색 (gpt-6-luna), LLM 시작점 기반 triplet 확장 검색 (DeepSeek/OpenRouter)

1. 전체 테이블명·설명과 질의·최근 히스토리를 LLM에 입력해 관련도 순으로 시작 테이블 선택
2. 선택 결과의 이름 검증·중복 제거 후 시작점 수를 `top_k`개 이하로 제한
3. 공급자별 RDF에서 시작점을 포함해 관계를 양방향으로 `max_hop`까지 확장
4. 방문한 테이블의 합집합 전체에 원본 DDL·설명을 매핑하고 카탈로그 순서대로 반환

- 온라인 LLM 호출: 시작점 선택 1회; 최종 LLM 재선별 없음
- 평가 설정: 두 공급자 모두 시작점 상한 1개, 최대 1-hop·2-hop 비교
- 반환 개수: 확장 후보 전체; 시작점이 1개여도 최종 반환은 1개나 5개로 제한되지 않음
- 예외 처리: 시작점이 없으면 빈 결과 반환; 독립 테이블도 시작점으로 선택 가능
- 기존 두 차례 LLM 선택 방식과의 차이: 관계 확장 후 LLM으로 후보를 다시 줄이지 않음

### 2.6. 임베딩 시작점 기반 triplet 확장 검색

- 검색 기능: 임베딩 시작점 기반 triplet 확장 검색 (bge-m3), 임베딩 시작점 기반 triplet 확장 검색 (text-embedding-3-small)

1. 저장된 triplet 임베딩 인덱스와 현재 카탈로그·RDF 로드
2. 질의·최근 히스토리 임베딩 후 테이블별 최고 triplet 유사도로 시작점 순위 산출
3. 순위 상위 `top_k`개의 고유 테이블을 시작점으로 선택
4. 현재 RDF의 관계를 시작점에서 양방향으로 `max_hop`까지 확장
5. 전체 확장 후보의 원본 DDL·설명을 카탈로그 순서대로 반환

- 온라인 LLM 호출·최종 재선별: 없음; 관계 사전 생성에는 공급자별 LLM 사용
- 평가 설정: 각 모델의 시작점 상한 1·2개와 최대 1·2-hop 조합
- RDF 선택: bge-m3 계열은 일반 RDF 부재 시 OpenRouter RDF로 대체; OpenAI 계열은 OpenAI RDF 사용
- 검색 자료 구분: 시작점은 triplet 인덱스로 선택하고 관계 확장은 현재 RDF로 수행; 과거 인덱스 관계와 RDF의 자동 동기화 없음
- 최종 반환 수: 시작점 상한과 별개; 고정 top-5 제한 없음

### 2.7. `top_k`·`max_hop`의 해석

| 검색 계열 | `top_k`의 의미 | 이번 평가 설정 | 최종 반환 |
|---|---|---|---|
| 스키마·triplet 임베딩 검색 | 최종 반환 테이블 수의 상한 | 5 | 모든 문항에서 5개 |
| 전체 스키마 LLM 검색 | 사용하지 않음 | 해당 없음 | LLM 선택 결과 |
| LLM 시작점 기반 확장 | 시작 테이블 수의 상한 | `top_k=1`, `max_hop=1,2` | 전체 확장 후보 |
| 임베딩 시작점 기반 확장 | 시작 테이블 수의 상한 | `top_k=1,2`, `max_hop=1,2` | 전체 확장 후보 |

- 1-hop: 시작 테이블에 직접 연결된 테이블까지 포함
- 2-hop: 직접 연결된 테이블의 이웃까지 추가; 모든 시작점의 방문 테이블 합집합 반환
- 탐색 방향: 관계의 들어오는 방향·나가는 방향 모두 사용; 이미 방문한 테이블은 중복 확장하지 않음
- 탐색 깊이와 반환 수: 최대 hop은 관계 이동 횟수의 상한이며 반환 테이블 수의 상한과 구분
- 최신 평가 제외 계열: RDF 확장 후 LLM 최종 재선별 방식, SQL 생성·실행 평가

## 3. 평가 지표와 결과 JSON 해석

- 평가 방식: 문항별 순차 요청
- 공통 요청 조건: `query=question`, `history=[]`, 타임아웃 300초
- 스키마·triplet 임베딩 검색 4종: 최종 반환 스키마 `top_k=5`; 실제 모든 문항에서 5개 반환
- 전체 스키마 LLM 검색 2종: `top_k`·`max_hop` 전달 없음; 반환 개수 가변
- LLM·임베딩 시작점 기반 확장 검색 4종: `top_k`는 시작점 수 상한, `max_hop`은 최대 탐색 깊이; 설정 조합별 12개 결과 비교

### 3.1. 결과 구조

| 필드 | 의미 |
|---|---|
| `format_version` | 평가 JSON 형식 버전; 현재 모두 `1` |
| `configuration.endpoint`, `base_url` | 평가한 검색 기능과 서버 주소 |
| `configuration.top_k` | 임베딩 검색은 최종 반환 개수; 관계 확장 검색은 시작점 수 상한; 전체 스키마 LLM 검색은 `null` |
| `configuration.max_hop` | 관계 확장 검색의 최대 hop 수; 관계 확장을 쓰지 않는 결과는 `null` 또는 필드 없음 |
| `configuration.timeout_seconds` | 문항별 요청 타임아웃 |
| `configuration.dataset_path`, `dataset_sha256` | 입력 위치와 파일 바이트 전체의 SHA-256; 공백·직렬화 형식 변경에도 해시 변경 가능 |
| `state` | 실행 상태인 `running`, `interrupted`, `complete`; 검색 정답률과 별개 |
| `started_at`, `updated_at` | 실행 시작·마지막 저장 시각; UTC 오프셋 포함 |
| `summary` | 전체 처리 현황과 성공 응답의 집계 지표 |
| `results` | 문항별 질문·정답·예측 테이블·지표·처리시간·오류 |

- 실행 시각 해석: 재개·중단·저장 비용 포함 가능; 시작·갱신 시각 차이를 순수 검색시간으로 사용하지 않음

### 3.2. 문항별 검색 품질

- 표기: 정답 테이블 집합 `G`, 검색된 테이블 집합 `P`

| 지표 | 계산 | 의미 |
|---|---|---|
| `tp` | `len(G ∩ P)` | 올바르게 찾은 정답 테이블 수 |
| `fp` | `len(P - G)` | 정답에 없는 추가 테이블 수 |
| `fn` | `len(G - P)` | 찾지 못한 정답 테이블 수 |
| `recall` | `TP / (TP + FN)` | 필요한 테이블 중 검색으로 확보한 비율; 본 비교의 주요 지표 |
| `precision` | `TP / (TP + FP)` | 반환한 테이블 중 정답의 비율 |
| `f1` | `2 × TP / (2 × TP + FP + FN)` | Precision·Recall을 함께 반영한 지표 |
| `exact_match` | `G == P` | 누락·불필요한 추가가 없는 완전 일치 여부 |

- 분모가 0인 비율: `0.0` 적용
- 집합 비교 방식: 중복 테이블·반환 순서의 점수 영향 없음; 테이블명 대소문자 자동 보정 없음
- 평가 제외 지표: MRR·nDCG, 컬럼 검색 정확도, SQL 실행 정확도
- 계산 예시: 정답 `{A, B}`, 예측 `{A, C, D}` → TP=1, FP=2, FN=1
- 예시 점수: Recall 50.00%, Precision 33.33%, F1 40.00%, 완전 일치 `false`
- 완전 일치 조건: Recall 100% 확보와 불필요한 추가 테이블 부재를 모두 충족

### 3.3. 집계 지표와 처리 현황

| `summary` 필드 | 의미 |
|---|---|
| `total_count` | 입력 전체 문항 수 |
| `evaluated_count` | 성공·실패를 포함한 저장 결과 문항 수 |
| `success_count`, `failure_count` | 정상 응답 검증 성공 수·오류 수 |
| `pending_count` | `total_count - evaluated_count`; 아직 결과가 없는 문항 수 |
| `success_rate` | `success_count / evaluated_count`; 검색 정답률이 아닌 응답 처리 성공률 |
| `macro.precision`, `macro.recall`, `macro.f1` | 성공 문항별 각 지표의 단순 평균 |
| `micro.tp`, `micro.fp`, `micro.fn` | 성공 문항 전체의 TP·FP·FN 합계 |
| `micro.precision`, `micro.recall`, `micro.f1` | 전체 TP·FP·FN 합계로 계산한 지표 |
| `exact_match_rate` | 성공 문항 중 완전 일치한 비율 |
| `mean_latency_seconds` | 성공 문항의 클라이언트 측 요청·응답 처리시간 평균(초) |
| `mean_api_elapsed_time` | 성공 문항 중 유효한 서버 `elapsed_time`의 평균(초) |

- Macro 집계: 문항별 동일 비중; **Macro F1은 문항별 F1의 평균**
- Micro 집계: 테이블 출현 횟수 합산; 정답·예측 테이블이 많은 문항의 영향 증가
- 클라이언트 시간 범위: HTTP 요청 전부터 응답 검증·지표 계산 후까지; 네트워크 왕복·클라이언트 처리 포함
- 서버 시간 범위: 서버가 보고한 API 내부 처리시간
- 시간 집계 제외: 사전 테이블 임베딩·triplet 생성·triplet 인덱싱
- 실패 문항 처리: 품질·평균 지연 지표에서 제외; 실패를 0점이나 타임아웃 시간으로 포함하지 않음
- 미집계 값: 성공 문항이 없으면 품질·평균 지연 지표 `null`; 유효한 서버 시간이 없으면 서버 평균 `null`
- 결과 확인 원칙: 품질 지표와 성공률·실패 수를 함께 확인

### 3.4. 개별 결과와 실패 원인 확인

- 문항 식별: `index`, `id`, `question`
- 정답·검색 결과 비교: `expected_tables`, `predicted_tables`
- 문항별 품질: `metrics`의 TP·FP·FN, Recall·Precision·F1, 완전 일치 여부
- 처리시간·시각: `latency_seconds`, `api_elapsed_time`, `completed_at`
- `status=success`: HTTP 성공, API 성공 상태, 반환 목록의 형식·길이 검증 통과
- 성공 상태의 의미: 정답 테이블 선택 여부와 별개; 빈 목록도 정상 형식이면 성공 처리 가능
- `status=error`: `http_status`, `error.type`, `error.message`로 원인 확인; 예측 테이블·지표는 `null`
- 주요 오류 유형: `http_error`(HTTP 오류), `api_error`(API 오류 상태), `invalid_response`(응답 형식 오류), 연결·타임아웃 예외
- 재개 처리: 성공 결과 재사용, 실패·미평가 문항 재호출
- 재개 검증: 검색 기능·서버 주소·`top_k`·`max_hop`·데이터셋 해시 등의 일치 여부 확인
